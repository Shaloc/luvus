---
title: Remote Sessions
description: Install Luvus on a remote host, connect over SSH, reopen named sessions, and troubleshoot common connection problems.
---

Luvus can keep the server, panes, agents, layouts, and scrollback on another
machine while your current terminal acts as the client. The normal interactive
command is:

```sh
luvus --remote devbox
```

Luvus launches your local `ssh` command, starts or finds the Luvus server on
`devbox`, and attaches the current terminal to it. It does not open a public
port, configure SSH forwarding, or require another daemon.

## Choose the right remote workflow

| What you want | Use |
|---|---|
| Register a reusable, named remote session | `luvus session remote add devbox api` |
| Control remote panes, agents, or worktrees from the local CLI | `luvus --host devbox --session api pane list` |
| Automatically show all same-name local and remote sessions together | `luvus session merge on` |
| Open the full remote Luvus interface from a computer with Luvus installed | `luvus --remote devbox` |
| Open a specific named session | `luvus --session api --remote devbox` |
| Connect from a phone that only has an SSH app | SSH to the host, then run `luvus` there |
| Send one JSON automation request | Pipe the request through `ssh devbox luvus uhp proxy` |
| Build an independent remote or mobile client | Use [`luvus uhp access`](/docs/uhp/remote-access/) with a secure transport provider |

Use managed sessions when you want a reusable identity, CLI control, or merge
mode. Use raw `--remote` for a one-off full-screen attach. UHP Access is for
application developers, not a prerequisite for interactive SSH sessions.

## Managed remote sessions

Managed remotes use a literal `Host` alias declared in `~/.ssh/config`. Luvus
stores that alias rather than the resolved `HostName`. The UI shows the actual
session name with remote/host tags. `remote-<host>-<name>` remains available as
a legacy CLI routing name:

First open **Settings → Remote** and select the hosts you want Luvus to use.
No hosts are enabled by default. The list reads local SSH configuration without
connecting to its entries. New Remote Session shows only enabled aliases;
`--host` and canonical remote session attaches enforce the same selection.
Checking a host connects and discovers its existing sessions. Settings shows
the session count or connection error. Opening the session switcher, or pressing
`r` there, refreshes the list, including sessions created independently on the
remote host. There is no idle polling and no connection to unselected hosts.

Local **Settings → Theme** and **Settings → Language** changes synchronize
the selected value to all running
sessions on connected selected hosts, including when the focused workspace is
remote. No other configuration is copied, and received patches do not fan out
again. See [theme synchronization](/docs/guides/themes/#connected-remote-machines).

You can also select and connect a configured SSH alias from the CLI:

```sh
luvus host add devbox
luvus host add devbox --install
# Only after explicit installation authorization, for unattended automation:
luvus host add devbox --install --yes --json
```

`host add` saves the alias in the local managed-host selection and discovers
existing remote sessions; it does not create a session. `--install` permits
an installation offer only if the compatible fork binary is missing. Alternatively,
enable **Settings → Remote → Offer Luvus installation when selecting a host** before
selecting a host (or running `host add`). This policy defaults to **off**;
changing it alone never starts installation. Before any install/update, the UI
asks whether to proceed for that specific host, with **Cancel** selected by
default. The CLI asks `[y/N]`; non-interactive execution requires explicit
`--install --yes`. The saved policy never bypasses confirmation. A failed host remains selected
so its connection error can be inspected and retried.

Installation runs the bundled fork installer via SSH. It detects the remote
platform, supports **macOS arm64/aarch64** and **Linux x86_64**, verifies SHA-256,
and atomically replaces `~/.local/bin/luvus` with a backup of any previous
regular file. It downloads only from `Shaloc/luvus` releases, needs remote
`curl` or `wget`, and does not need `gh`, `sudo`, SCP, or a remote build.
Windows and other architectures fail without replacing the installation.
An already compatible binary is left alone; this is not automatic updating.

SSH authentication/host-key failures never trigger installation or bypass
verification. Once installation has started it is bounded but disconnecting
does not roll it back. **No server is started, stopped, or restarted** by host
installation; an older running server may still need a user-triggered restart.
Ordinary discovery, config reload, and background reconnect never install.
`host add` is a local setup command, not a `--host`-routable UHP method.

```sh
luvus session remote add devbox api
# registered name: remote-devbox-api

luvus session remote list
luvus session attach remote-devbox-api
```

You can also open the session switcher and choose **New Remote Session**. The
form lets you select a configured host and enter the actual remote session name.
Merge is a global setting, not a per-session form option. This creates a new remote session after validating the
remote binary. Existing sessions are already in the switcher. The CLI `remote
add` command starts or reuses its selected session.

Managed session attaches keep the **local** interface and session switcher.
The local prefix still opens the menu, so you can switch from remote to remote
or back to local. SSH transports control and workspace frames in the background;
it does not replace your terminal with the remote host's full Luvus interface.
Workspace prefix suffixes, including `?`, digits and custom bindings, are
interpreted by the owner's prefix handler even when its prefix differs from
the display client's. Global session navigation and local Settings/Agents stay
local. Pressing the prefix twice sends the owner's configured prefix once.
The bottom status bar identifies the active remote host and actual session.

To also show the current tab position, pane ID, and agent type/state, select
**Settings → Layout → Luvus Bar → Current tab / pane → Bottom**. It defaults
to Off and uses the focused owner's metadata in local, direct remote, and
merge layouts. Tab positions are 1-based; pane IDs are the owner's opaque IDs,
not the local projection's ID. Shells and native views have no agent label.
Metadata is hidden while disconnected or while topology and displayed focus
do not agree. Mode-specific key guidance takes precedence on the status line;
narrow rows use compact labels (`t2 p27`) or the normal bar overflow.

The existing CLI/UHP bar placement commands control the same preference on
the display server:

```sh
luvus bar move --id core:focused-pane --region bottom-right
luvus bar move --id core:focused-pane --region off
```

The Agents highlight follows the pane selected on the workspace's owner, not
the agent's working/idle state. Mouse, tab, prefix and CLI/API focus changes
update it through the existing event subscription without periodic polling.
Clicking an agent also leaves keyboard list navigation, matching local rows.

After a connected owner restarts or an SSH bridge fails, the local presentation
automatically reconnects both its display and event subscription. Retries back
off from 250 ms to 10 seconds, only while disconnected; healthy sessions do not
poll. The last frame stays visible with a connection notice, and recovery reads
a fresh owner snapshot before restoring workspace input, size and agent state.
Keys typed while disconnected are not queued or replayed. Reconnection uses
existing-only bridges: it never starts a stopped owner, installs a binary or
bypasses the managed-host/version checks. A stopped owner remains stopped until
you start it. Deselecting its host or removing its merge connection cancels retries.
An initial open that fails before connecting still reports its setup error.
Authentication, host-key and incompatible-protocol errors stop automatic retries
and retain their SSH diagnostic. Fix SSH access or explicitly update the owner,
then refresh the session selector. Background bridges never answer prompts or
accept an unknown host key.

When both ends support `projection.v1`, hidden workspaces keep their metadata
and agent event subscriptions but pause terminal frames. Switching or resizing
waits for a frame matching the owner generation, activation epoch and viewport
before forwarding pane input. The Agents focus marker comes from that frame.
Viewing it clears a native Done notification on the owner; it does not change
working/blocked states or override an external agent status report. The display
input queue is bounded by message count and bytes; a stalled write disconnects
that owner connection rather than retaining an unbounded paste/input backlog.

Merge uses an existing same-name local owner (running or saved); it never
creates a local session merely because you opened or created a remote one.
If that name exists only remotely, the switcher and CLI attach keep using the
remote presentation view. Turning merge off and on follows the same rule.
The implicit `default` list entry and a global configuration directory alone
do not count as an existing local owner. Existing local records are preserved;
this does not automatically remove copies created by older versions.

### Stop versus delete

Stopping a session ends its server but retains its saved state and logs, so a
`stopped` row remains available to reopen. Remote rows show their owner's
`running`/`stopped` state. In merge mode, the row labels the local machine and
each remote separately; a local `stopped` does not mean every remote is stopped.
A `?` means discovery failed, not proof that the owner stopped.

Right-click a session row (or select it and press `d` / Delete) to open its
owner actions. Running non-current owners offer **Stop**; stopped named owners
offer **Delete**. A merged row lists each eligible machine separately. Deletion
requires a second confirmation naming the machine and actual session; Cancel
is selected by default. It removes that owner's saved session and logs, not
project directories or other machines' same-name sessions. The owner rechecks
that the session is stopped before deleting. The `default` session cannot be
deleted. Unknown/unreachable owners do not offer destructive actions.

The equivalent commands, run only after choosing the owner, are:

```sh
luvus session delete review
ssh devbox 'luvus session delete review'
```

Public CLI/UHP session inventories export owner namespaces, not the local
presentation servers used by managed attaches. Presentation identity is saved
independently of workspaces and survives stop or remote-registration removal.
Literal owner names beginning with `remote-` remain valid and discoverable.
Unmarked legacy namespaces are not guessed from their names or deleted.

### Flat or tree workspace sidebar

Choose **Settings → Layout → Workspace display** to switch live between:

- **Flat** (default): the existing workspace list with `[host]` labels.
- **Tree**: local machine first, then SSH-alias groups. Each group keeps the
  existing pinned-workspace and nested-worktree ordering; workspace names do
  not repeat the hostname. Remote group dots reflect existing transport state:
  green is connected, amber is connecting, and coral indicates a disconnected
  projection. Only machines with workspaces in the current view are listed.

Click a machine heading to fold or unfold it. With WORKSPACES keyboard focus,
use Up/Down to navigate, Enter/Space on a heading to toggle it, Left to collapse
it (or move from a workspace to its heading), and Right to expand it. Enter on
a workspace still selects its owner; `a` still opens its workspace menu.
Selecting a hidden workspace through another control reveals its machine.
Workspace jump and next/previous shortcuts follow machine/worktree order in
tree mode, including folded workspaces, and reveal the selected machine.

The display preference is saved as `layout.workspace_display` (`flat` or
`tree`); machine folds are temporary UI state. Both modes respect the path-row
toggle and either dock position. This is independent of the global merge
setting: changing the presentation does not merge sessions, connect hosts, or
change API workspace indices. The session selector and Agents dock retain
their owner labels.

Hiding a sidebar while viewing a remote workspace retains a local reopen
chevron. Its navigation row is outside the owner viewport, so expanding it
cannot click a remote tab or terminal. The row disappears when no sidebar
needs reopening; mouse coordinates and PTY dimensions follow the updated area.

Managed remotes require compatible modified Luvus protocols, not identical
package versions. Transport 9 remains available as a legacy fallback. Transport
10 owners advertise the optional `projection.v1` feature in `remote_display`
within `session.snapshot` and `uhp.capabilities`; older owners retain their
existing display behavior without the new presentation guarantees or pause
optimization. An absent, incompatible or unmodified binary produces an install
diagnostic. Luvus never copies a binary with `scp`.

Use `--host` to send server-backed CLI commands directly to that host. The
selector works with workspace, tab, pane, agent, files, Git, DIFF, worktree,
task, lease, wait, search, event, module, bar, UI, Mission Control, and UHP
server controls. Server lifecycle commands use the same selector too:

```sh
luvus --host devbox --session api pane list
luvus --session api worktree list --host devbox
luvus --host devbox --session api workspace open /srv/api
luvus --host devbox --session api server status
```

Ordinary managed control requests and workspace frame connections require an
already-running owner; they never start or restart it implicitly. Explicitly
opening a session, `remote add`, and server lifecycle commands remain the
entry points for starting it.

Commands that manage client-machine files or registries intentionally reject
`--host`: session registration and merge settings, themes, skills, updates,
integrations, `doctor`, module install/search, and `uhp access`/`schema`. Run an
explicit `ssh <host> luvus ...` command only when you intend that host-local
operation. Host-profile methods sent through `uhp proxy` are also rejected;
`--host` routes only the selected session's server API.

For commands containing free text or pass-through arguments, put `--host`
before the command so a literal `--host` in the payload remains user data:

```sh
luvus --host devbox --session api agent prompt reviewer "check --host handling"
luvus --host devbox --session api pane run 7 tool --host literal
```

### Merge same-name sessions

Merge mode keeps the local session as the UI owner and adds every discovered
remote session with the same actual name. Each workspace remains wholly owned
by either the local server or one remote server; Luvus does not copy its files
or PTYs. Remote workspace rows carry a `[host]` tag, while their remote branch
and path are shown from that host.

```sh
luvus session remote add devbox api --merge
luvus session remote add buildbox api --merge
luvus session attach api

# Change the saved mode later.
luvus session merge off
luvus session merge on
```

The CLI toggle saves the mode and refreshes an already-running local server.
The same applies when adding or removing a registered remote. No server restart
is needed. Turning merge off or deselecting a host in Settings removes its
local projections and disconnects their bridges, leaving the remote server and
panes running. New registration and merge discovery are user-triggered; there
is no periodic scan or connection to every SSH host. Settings → Remote has a
single global merge toggle, automatically grouping every same-name session.
Enabling it from a standalone remote view switches to the matching local
session and shows the local and remote workspaces together.

Closing a projected remote workspace hides that projection in the current
local run; it does not close the workspace or its processes on the remote
owner. Use an explicit `--host` command when you intend to mutate remote state.

The workspace **+** action in merge mode first asks which enabled host should
own the workspace (or **Local machine**). Its folder browser reads that owner's
filesystem. Selecting the currently viewed remote owner preserves the active
workspace as the starting directory. Directory rows, parent navigation and
confirmation/cancellation are clickable; narrow dialogs retain their essential
footer controls instead of clipping Cancel off-screen.

### Worktrees and image paste

**Open worktree** in a workspace's context menu lists its Git worktrees with
branch (or detached HEAD) and path, including checkouts outside Luvus's managed
worktree directory. Already-open entries are marked and selecting one focuses
it. The list loads asynchronously; choose a row or cancel. For a remote
workspace it comes from its owner host, not the local filesystem. Use workspace
**+** / **Open Workspace** to browse an arbitrary directory instead.

**Ctrl+V** reads a clipboard image on the display client, sends the bytes to the
pane's owner, and pastes a private owner-local file path. Empty terminal paste
events also try image paste. Images are limited to 16 MiB and remain in the
owner session's `clipboard/` directory so agents can read them after detach.
PNG, JPEG, GIF, WebP and BMP are supported where the OS clipboard exposes them.
Linux uses `wl-paste` or `xclip`; macOS uses `osascript`; Windows/WSL uses
PowerShell. Missing tools or no image preserves normal input. Ctrl+Enter is
unchanged. In Kitty, a headless SSH display client can use the optional official
`kitten clipboard` executable on that client host to request PNG clipboard bytes
over [OSC 5522](https://sw.kovidgoyal.net/kitty/clipboard/). Kitty controls access
and may ask for permission; Luvus does not bypass it. Other headless clients need
native desktop clipboard access. Clipboard reads happen only on paste.

Install the optional helper from **Menu → General → Kitty clipboard (client)**,
or run `luvus kitten install` on the display-client machine (`luvus kitten status`
checks it). Opening General only checks local availability; it does not download
anything or read your clipboard. Explicit installation downloads the pinned
official Kitty 0.48.2 helper with SHA-256 verification into the display client's
Luvus home, under `tools/kitten`, without replacing an existing PATH installation,
changing PATH, or restarting a session. Luvus uses the private helper immediately.
Linux and macOS x86-64/ARM64 installation targets are provided; other platforms
report unsupported. The install runs on the display client even when the server
is reached through SSH; in a managed remote workspace use the outer Settings,
not the owner's projected Settings. This local-only command rejects `--host`.
Kitty may still ask you to authorize the clipboard read. Denied reads, missing
helpers and non-image clipboards preserve the child application's Ctrl+V;
an SSH-hosted child may then report its own X11 clipboard error.

Child OSC52 text-copy requests, including Neovim yank, are forwarded to the
display client's clipboard from local and remote panes. They do not require
the image helper. Clipboard reads (`OSC 52 ... ?`) and primary-selection writes
are not forwarded.

In merge mode, the workspace **+** first asks for Local machine or an enabled
SSH host. Worktree, rename, delete-worktree, TaskBoard and Mission Control
actions run on the selected workspace's owner. The Agents dock combines native
owner-reported statuses and marks remote rows with the host; clicks focus the
owner's pane. `agent list` includes `host`, `owner_session`, and `owner_pane` for
remote rows. Follow up with those owner selectors and `--host`, not the qualified
local presentation row ID. Remote FILES views do not expose a stale local tree.

### Kitty graphics preview

Fork graphics builds report `transport=11` with
`luvus --version --remote-session-protocol`. Use Kitty 0.28 or newer on the display
machine and matching graphics builds on remote owners. An older managed owner
can still display text, but cannot supply graphics. For an SSH-hosted display
client, preserve `TERM=xterm-kitty`; changing TERM in the child pane alone does
not enable graphics on the outer client.

Luvus accepts direct-transfer (`t=d`) RGB, RGBA and PNG images, including zlib
compression for RGB/RGBA. It forwards compressed pixels without decoding them
into its text grid. File and shared-memory queries return unsupported so tools
such as terminal-browser can select inline transfer. No kitten helper is needed
for rendering; the clipboard helper described above is a separate feature.

Keyboard input also follows the child's negotiated Kitty modes. Applications
requesting report-all plus associated text receive printable text in the key
event, including case and Unicode, while shortcuts remain non-text events.
This allows terminal-browser login fields to accept normal typing, not only
paste. In managed remote panes the owner performs this encoding, so update
the owner binary as well as the display machine when applying input fixes.

Images are clipped to pane cells and compose with local and remote menus.
Image-only updates retain the client's image IDs and do not resend unchanged
text. `NO_COLOR` keeps ordinary text colorless while retaining the RGB metadata
needed by Kitty's Unicode image placeholders. Closing a graphic application or
switching workspaces removes only the images owned by that Luvus display client.

Inline-image clients can use `U=1` virtual images with a default placement ID
and explicit Unicode placeholder row/column coordinates. Luvus preserves those
coordinates while remapping image IDs per pane and display. This supports
tele-style message scrolling and mosaic windows without decoding or cropping
pixels. Erasing the text does not delete the reusable image; explicit deletion
and replacement update its lifetime. Retained placeholder text can also display
in scrollback while its image remains in the bounded owner cache.

The tele path is verified with independent protocol fixtures derived from its
[renderer contract](https://github.com/sorokin-vladimir/tele/blob/98d7489982aa9a5c094d7430ccebc5bcf2f303f4/internal/ui/media/kitty.go),
not by installing, compiling or logging into tele. If the child's environment
does not identify Kitty, start it with `TERM=xterm-kitty tele` or select tele's
Kitty photo mode. Full application acceptance remains a user test.

This is a graphics preview, not complete Kitty protocol support. Sixel, animation
commands, relative placements, non-default virtual placement IDs, omitted
placeholder coordinates, nonzero z-order, source-pixel cropping, stretched
ordinary placements, compressed PNG and ordinary-image scrollback are not
supported. A placement can span at most 297 columns and 297 rows; larger
placements are rejected instead of incorrectly tiling the image. Pane-edge and
scroll-region clipping remain supported without changing source coordinates.
Uploads are bounded to
32 MiB of encoded data and 16 million pixels per image, with 32 images and 128
placements per terminal; the composed display has a 48 MiB encoded-data bound.
High-resolution scrolling still depends on the application's pixel encoder,
network bandwidth and Kitty rendering. Passing transport tests does not establish
Chromium performance or guarantee 60 FPS. terminal-code requires separate
application-level verification.

Incomplete image transfers and graphics capability queries do not request a
terminal repaint or scrollback compaction. A completed image mutation still
wakes the existing renderer immediately, subject to its normal frame cap and
backpressure. Opening a synchronized frame does not repaint the old screen;
committing that frame publishes its buffered output. The renderer consumes old
output notifications before projection while keeping trailing notifications
for output that arrives during projection. Text, input modes, titles and
clipboard effects interleaved with uploads keep their normal handling. This
applies to local and managed remote owners; it does not reduce the application's
full-image payload size.

To compare the same isolated PixelEngine workload between builds on Linux:

```sh
LUVUS_TEST_PIXEL_PERF=1 LUVUS_TEST_PIXEL_PERF_SIZE=268x70 \
LUVUS_TEST_PIXEL_BINDING=/path/to/terminal-browser/browser/native/pixel.node \
python3 scripts/test-remote-sessions.py target/release/luvus --graphics-only
```

The test uses private homes and a local SSH substitute under `target/`, not
configured hosts or production sessions. It measures simple canvas updates
arriving at the thin client's output, not the physical display frame rate.

### Which machine owns a control?

The local Settings window, session/workspace navigation, Agents All/Active and
workspace-scope filters stay local. Next Attention cycles through waiting agents
across the visible local/remote workspace group. The same rules apply to a
standalone managed remote session and a globally merged session.

Workspace content belongs to its owner: tabs, panes, FILES/DIFF, Git, TaskBoard,
Mission Control, and the owner's module docks and bars use the remote server.
Their mouse actions and `--host <host> --session <name>` CLI commands act there,
not on an identically named local directory. The remote workspace's context
menu provides explicit **Settings** and **Module actions** entries for its owner;
opening the ordinary global Settings window still changes local Luvus
configuration. Installing a remote integration or module remains an
explicit action in that owner's settings.

The Agents dock includes remote live agents, pending scheduled-agent rows and,
in All mode, resumable native agent history. Remote rows show their host. Click
a scheduled row to open its owner's automation detail; click a history row to
resume on that owner. A history row's **Close** only dismisses that entry from
the owner's history list for the current run; it does not delete the native
agent session on disk. Local history always resumes locally, even if a remote
workspace is currently focused.

Remote live-agent Rename, Close and Pin/Unpin act on the owner. Pin uses the
owner's existing per-session pin state and its ordering is reflected locally.
The row's workspace-scope option controls the visible local Agents dock;
**Module actions** opens the owner's agent menu. Closing a projected workspace
still only hides the local projection, as described above; it is not the same
as closing one of the owner's live agent panes.

`--remote` remains the raw compatibility escape hatch. Unlike managed
`--host`, it may use an arbitrary OpenSSH destination and does not register a
canonical remote session or participate in merge mode.

## First connection

### 1. Install Luvus on both machines

The computer in front of you needs Luvus so it can run the local client. The
remote host needs Luvus so it can own the server and panes.

On macOS or Linux, run this on each machine:

```sh
curl -fsSL https://luvus.dev/install.sh | sh
```

Other supported installation methods are listed in the
[installation guide](/docs/getting-started/installation/).

### 2. Confirm ordinary SSH works

Use the same destination that you plan to give Luvus:

```sh
ssh devbox
```

After signing in, verify the remote installation:

```sh
luvus --version
exit
```

You can perform the same check without opening an interactive shell:

```sh
ssh devbox luvus --version
```

:::note
Some remote shells omit user installation directories from their
non-interactive `PATH`. `luvus --remote` handles this on POSIX hosts by checking
`~/.local/bin`, `~/.cargo/bin`, `~/.nix-profile/bin`, `/usr/local/bin`, and the
usual Homebrew paths when the first launch cannot find `luvus`.
:::

### 3. Attach

Run this on your local machine:

```sh
luvus --remote devbox
```

The first connection starts the default remote Luvus server if needed. Later
connections attach to that same server, so its workspaces, tabs, panes, and
agents remain available.

## SSH destination examples

`<host>` accepts the same destination forms as OpenSSH:

```sh
# An alias from ~/.ssh/config
luvus --remote devbox

# A DNS name with an explicit user
luvus --remote alice@dev.example.com

# An IP address with an explicit user
luvus --remote alice@203.0.113.10
```

Any arguments after the host are passed to `ssh`. Luvus places them before the
SSH destination when it launches the command:

```sh
# Custom port
luvus --remote alice@dev.example.com -p 2222

# Specific private key
luvus --remote alice@dev.example.com -i ~/.ssh/work_ed25519

# Port and key together
luvus --remote alice@203.0.113.10 -p 2222 -i ~/.ssh/work_ed25519

# Connect through a bastion host
luvus --remote private-devbox -J bastion.example.com

# Use a separate SSH configuration file
luvus --remote devbox -F ~/.ssh/work-config
```

Passwords, hardware-key confirmation, and host-key prompts are still handled by
`ssh`. Luvus does not read or store those credentials.

## A reusable SSH configuration

An SSH alias keeps the Luvus command short and lets normal SSH tools reuse the
same settings. Add this to `~/.ssh/config` on macOS or Linux, or
`%USERPROFILE%\.ssh\config` on Windows:

```ssh-config
Host devbox
  HostName 203.0.113.10
  User alice
  Port 2222
  IdentityFile ~/.ssh/work_ed25519
```

Test the alias first, then attach:

```sh
ssh devbox
luvus --remote devbox
```

ProxyJump, agent forwarding, host aliases, identity agents, and other OpenSSH
settings continue to belong in this file. If `ssh devbox` cannot connect, Luvus
cannot connect through that alias either.

## Platform notes

The remote command has the same shape on macOS, Linux, and Windows. In
PowerShell, quote a Windows key path when it contains special characters or
spaces:

```powershell
luvus --remote alice@dev.example.com -p 2222 -i "$HOME\.ssh\work_ed25519"
```

A Windows client needs the OpenSSH Client and `luvus.exe`. A Windows remote host
also needs OpenSSH Server, and `luvus.exe` must be on the non-interactive `PATH`
of the account used to sign in. The fallback search through POSIX user
directories applies only to macOS and Linux remote hosts.

## Raw named remote sessions

The command without `--session` targets the remote host's `default` session.
Select another independent remote server namespace by placing the global
session option before `--remote`:

```sh
luvus --session api --remote devbox
luvus --session frontend --remote devbox
luvus --session incident-42 --remote devbox
```

You do not need to create the session first. Luvus starts it when necessary and
reattaches to it on later runs of the same command.

To inspect the remote host's sessions without opening the TUI:

```sh
ssh devbox luvus session list
ssh devbox luvus session list --json
```

Inside a remote TUI, `Ctrl+Space t` opens the session switcher. Choosing a
different session starts it when needed and moves only the current client. The
previous session and its panes stay alive.

To stop another running session from the switcher, right-click it and select
**Stop**. This ends that session and its live panes without detaching the
current client. The current session cannot be stopped from this menu.

## Detach and reconnect

Press `Ctrl+Space q` to detach cleanly. Closing the local terminal, losing the
network, or putting a laptop to sleep also disconnects the client without
stopping the remote server.

Reconnect with the same command:

```sh
luvus --remote devbox

# Or reconnect to a named session
luvus --session api --remote devbox
```

Luvus adds bounded SSH keepalives automatically. A dead connection is detected
instead of remaining stuck indefinitely, and reconnecting does not create a
second copy of the selected server.

Stopping a remote server is different from detaching. It ends that session's
live PTYs:

```sh
# Stop the default remote session
ssh devbox luvus server stop

# Stop one named remote session
ssh devbox luvus --session api server stop
```

Use `server stop` only when you intend to stop the processes in that Luvus
session.

## What stays remote and what stays local

The remote server owns:

- workspaces, tabs, panes, PTYs, and terminal scrollback
- agent processes, detection, resume state, and orchestration
- the remote account's Luvus configuration and session data
- file, Git, DIFF, and search results for remote projects

With `luvus --remote`, the local attached client owns effects that should happen
where you are sitting:

- copied text goes to the local clipboard
- notifications and sounds play locally
- detected links open in the local browser
- each attached client uses its own terminal size and mobile or desktop layout

With the raw `luvus --remote` transport, the global finder searches that remote
Luvus home. In managed remote and merge mode, the local finder also queries the
displayed remote owners. Remote results have a host tag; files and output are
searched and opened on their owner, never against a same-named local path.
Activating an existing remote workspace keeps the local client attached.
Unavailable owners produce partial results and are not started by a search.

## Connect from a phone or tablet

A phone does not need a native Luvus installation when it already has an SSH
terminal such as Termius. Create a connection to the host in that app, then run
Luvus at the remote prompt:

```sh
luvus
```

For a named session:

```sh
luvus --session api
```

Luvus automatically switches to its mobile presentation when the terminal is
narrow enough. See [Mobile Sessions](/docs/guides/mobile/) for navigation,
Termius sizing, and the configurable width boundary.

## Run one remote UHP request over SSH

You do not need an access gateway to run a single automation request over an
SSH connection. `uhp proxy` reads one LF-terminated JSON request from stdin and
writes one response:

```sh
printf '%s\n' '{"id":"snapshot","method":"session.snapshot","params":{}}' \
  | ssh devbox luvus uhp proxy
```

Target a named session by selecting it on the remote command:

```sh
printf '%s\n' '{"id":"panes","method":"pane.list","params":{}}' \
  | ssh devbox luvus --session api uhp proxy
```

This is a convenient path for scripts and diagnostics. For persistent event or
terminal streams, use the owner endpoint locally on the host or connect a
reviewed secure transport provider through
[UHP Access](/docs/uhp/remote-access/).

## Troubleshooting

### `ssh` is missing locally

Run:

```sh
luvus doctor
ssh -V
```

Install an OpenSSH client using your operating system's package manager. On
Windows, enable the built-in OpenSSH Client optional feature if `ssh.exe` is not
already available.

### SSH authentication fails or times out

Remove Luvus from the equation and test the same destination and options:

```sh
ssh devbox
ssh -v devbox
```

For explicit options, remember that ordinary SSH places them before the host:

```sh
ssh -p 2222 -i ~/.ssh/work_ed25519 alice@203.0.113.10
```

The equivalent Luvus form places passthrough options after its host argument:

```sh
luvus --remote alice@203.0.113.10 -p 2222 -i ~/.ssh/work_ed25519
```

### Luvus is not found on the remote host

Confirm that it is installed for the same remote account:

```sh
ssh devbox luvus --version
```

On a POSIX host, inspect the common user locations if the command is absent:

```sh
ssh devbox 'command -v luvus || ls -l ~/.local/bin/luvus ~/.cargo/bin/luvus ~/.nix-profile/bin/luvus 2>/dev/null'
```

If none exists, install Luvus on the remote host. On a Windows remote host,
`luvus.exe` must be available to the account used by OpenSSH in its
non-interactive `PATH`.

### The connection closes immediately

Check both versions:

```sh
luvus --version
ssh devbox luvus --version
```

Update the older installation when they differ, then retry. Also run the plain
SSH command with `-v` to distinguish authentication, host-key, remote command,
and network failures.

### The wrong session opens

No selector means `default`. Put the selector before `--remote` and reuse the
same name when reconnecting:

```sh
luvus --session api --remote devbox
```

### A dropped connection does not stop the agents

That is expected. The remote server owns the PTYs and remains alive after the
client disconnects. Reattach with the same command. Use `server stop` only when
you intentionally want to end the session's live processes.

## Security model

Interactive remote sessions inherit OpenSSH authentication, encryption,
host-key verification, aliases, jump hosts, and policy. Luvus adds no public
listener and sends no owner socket path over the network. The remote bridge
exists only inside the SSH process, while the server endpoint remains private
to the remote operating-system account.

Do not expose `~/.luvus` sockets or Windows named pipes through a public tunnel.
For an independent client that cannot run through the interactive SSH bridge,
use the scoped, expiring pairing flow documented in
[Remote access and transport providers](/docs/uhp/remote-access/).

## Fork macOS build artifacts

The `Shaloc/luvus` fork provides a manual **Fork macOS ARM64 artifact** workflow
for `aarch64-apple-darwin`. It builds the selected commit and uploads a tarball
and SHA-256 checksum to that workflow run, retained for 30 days. The archive
contains `luvus`, its license, and `build-info.txt` identifying the source commit.
An isolated installation of the archive is smoke-tested on the macOS runner.

This workflow does not create releases or tags, publish packages, update
Homebrew taps, build the website, or dispatch downstream workflows. Existing
upstream CI and release workflows are unchanged. To keep a fork-only build
isolated, push its commit with `[skip ci]` and run this workflow manually; do not
run the upstream release scripts or installer to distribute the custom binary.

On Apple Silicon, verify the downloaded `.tar.gz.sha256` with `shasum -a 256 -c`,
extract the archive, and install its binary into your chosen PATH directory.
Check `luvus --version --remote-session-protocol` on each host: managed remote
connections need compatible fork protocols. Installing a binary does
not restart any existing server; restart is a separate, explicit operation.
